# mpflow 两个月计划

目标：2027 年 1 月，这个仓库有真实用户、有可验证的维护记录，可以拿去申请 Codex for Open Source。

一句话定位：**公众号发布的 `git push`**——本地写 Markdown，一条命令变成草稿，人确认后发布。

## 为什么是这个

| 判断维度 | 结论 |
|---|---|
| 分发 | 你在中文开发者社区，目标用户（技术公众号作者）就在里面 |
| 痛点 | 作者每次都要离开终端，把稿子复制进网页编辑器再粘回来 |
| 依赖形态 | Python 库 + CLI + MCP 三重入口，别人可以 import、可以包一层 |
| 合规 | 走官方开放接口，不模拟登录、不碰浏览器，无封号风险 |
| 维护成本 | 接口稳定，不会像爬虫那样三天两头坏 |

竞品：doocs/md、mdnice 是**网页编辑器**，解决排版但不解决流水线；`wechat_oa_mcp` 只是把几个接口壳了一层，没有工作流。

## 关键决策（已定）

1. 只做官方 API，不做浏览器自动化。
2. `publish` 必须人工确认，不做全自动群发——这是道德边界也是产品差异。
3. 排版引擎独立成模块 + 主题字典，方便社区贡献主题。
4. 首发做 Python；如果 MCP 客户端生态偏 TS，再加一个薄的 TS 包装。

## 8 周节奏

| 周 | 目标 | 可验证交付 |
|---|---|---|
| 1（11/04–11/10） | 验证 + 打通接口 | 用真实公众号跑通 `draft` → `publish` 全流程；找 5 个技术号作者聊一次 |
| 2（11/11–11/17） | MVP | 图片自动上传、主题系统、错误提示完善；发 v0.1.0 到 PyPI |
| 3（11/18–11/24） | 发布 | 写一篇「我如何用一条命令发公众号」；发掘金、V2EX、即刻、知乎 |
| 4（11/25–12/01） | 反馈迭代 | 按 issue 修；补 README 动图；加 GitHub Action 预览 |
| 5–6（12/02–12/15） | 扩展 | 草稿列表/更新/删除、发布后数据回看；做 2 个主题 |
| 7（12/16–12/22） | 生态 | 给 3 个内容工具提 PR 接入 mpflow；写 CONTRIBUTING + good first issue |
| 8（12/23–12/31） | 固化 | 文档站、示例库、v0.2.0；整理申请材料 |

## 成功判据（12 月底）

- [ ] PyPI 月下载 > 500（可从 pypistats 查）
- [ ] ≥ 3 个外部项目/issues 提到在用
- [ ] ≥ 100 star，且 issue 里有陌生人提需求
- [ ] 至少 2 个外部贡献者（非自己）
- [ ] 一次公开发布在中文社区获得可观测的传播（阅读量/转发）

达不到就诚实复盘：是选题问题、分发问题，还是执行问题。

## 申请材料（1 月准备）

1. 项目是什么、解决谁的什么问题
2. 使用证据：下载量曲线、下游依赖、外部 issue
3. 你的角色：commit 历史、review、release 记录
4. 拿到 Pro 后要做什么：具体到「用 Codex 做什么」

## 风险

- **风险：公众号接口对个人号能力有限**（部分接口需要认证服务号）。缓解：先把「草稿 + 排版」做扎实，发布能力按账号类型降级提示。
- **风险：需求可能没有想象中大**。缓解：第 1 周先找人聊，别闷头写完。
- **风险：官方或大厂工具覆盖**。缓解：占据"开发者/agent 原生"这个位置，这是大厂不会做的。
