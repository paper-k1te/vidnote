# GitHub 协作入门：Issue、PR 与"看起来成熟"

> 这份笔记解决一个问题：怎么从"只会 clone 别人的代码"变成"能把自己的改动合进别人的项目"。
> 后者是社区里最有说服力的能力证明，而且**无法伪造**。

## 一、三个基础概念

| 概念 | 是什么 | 类比 |
|---|---|---|
| **Repo（仓库）** | 一个项目的代码 + 历史记录 | 一栋房子 |
| **Fork** | 把别人的仓库复制一份到自己名下 | 抄一份图纸回去改 |
| **Branch（分支）** | 仓库里的一条独立开发线 | 在旁边搭个工棚试改 |
| **Issue** | 问题单：bug 报告或功能请求 | 报修工单 |
| **PR（Pull Request）** | 修改申请：请求把你的分支合并回主仓库 | 把改好的图纸递回去，"你看看要不要用" |

## 二、Issue 怎么写才算专业

维护者判断一个人靠不靠谱，第一眼看的就是 issue 质量。一个好 issue 包含：

1. **环境**：操作系统、版本号、语言版本
2. **复现步骤**：编号列出，越具体越好
3. **预期结果** 与 **实际结果**
4. **补充信息**：日志、截图、特殊情况（比如"路径含中文时触发"）

模板：

```markdown
**环境**：Windows 11 / Python 3.13 / 项目版本 0.4.1

**复现步骤**：
1. 运行 `xxx`
2. 看到 `yyy`

**预期**：……
**实际**：……

**补充**：……
```

反例（会被忽略或关闭）：

> "用不了，报错了，求修复"

## 三、提 PR 的完整流程

```powershell
# 0. 网页上点 Fork
git clone https://github.com/<你的用户名>/<项目>.git
cd <项目>

# 1. 建分支，命名体现意图
git checkout -b fix/typo-in-readme

# 2. 改代码，跑测试
#    （先读 CONTRIBUTING.md，很多项目有格式要求）

# 3. 提交
git add .
git commit -m "fix: correct the install command in README"

# 4. 推到自己的 fork
git push origin fix/typo-in-readme

# 5. 网页上点 "Compare & pull request"，写标题和描述
```

### PR 描述模板

```markdown
## 改了什么
修正 README 里错误的安装命令

## 为什么
原命令 `pip install x` 会安装到错误的包

## 怎么验证
在干净的 venv 里执行新命令，能正常安装

Fixes #123
```

`Fixes #123` 会在 PR 合并后自动关闭对应 issue。

## 四、Review 阶段会发生什么

- 维护者可能要求改动（"这里加个测试"）——在同一分支继续 commit + push，PR 会自动更新
- 可能被要求 rebase / squash
- 可能几周没回应，这是正常的，**不要催**
- 可能被拒绝，也不代表你不行，可能只是方向不合

## 五、新手最容易踩的三个坑

1. **一个 PR 改十件事**——没人愿意审，拆小。
2. **在 main 分支上直接改**——必须先开分支。
3. **催维护者**——大家都是无偿的。

## 六、去哪里找活干

- 仓库的 `good first issue` / `help wanted` 标签
- 你正在用的项目的文档错别字（最容易被合并，用来练流程）
- 你自己踩到的 bug（最真实，因为你真的复现了）

## 七、一周练习计划

| 天 | 任务 | 目的 |
|---|---|---|
| 1 | 找一个你在用的项目，读它的 CONTRIBUTING.md | 了解规范 |
| 2 | 提一个文档修正 PR（改错别字/补一句说明） | 走通全流程 |
| 3 | 提一个带复现步骤的 issue | 练描述能力 |
| 4–5 | 修一个 `good first issue` | 第一次真实代码贡献 |
| 6–7 | 复盘：看维护者的 review 意见，改到合并 | 学会接受 review |

## 八、为什么这比 star 重要

- **merged PR 是第三方背书**：别人愿意把你的代码放进他的项目，这个判断无法自吹。
- **review 记录是公开的**：你的代码被资深开发者逐行点评过，这本身就是学习证明。
- **它证明你能在别人的规则下工作**：这是"成熟开发者"和"会写代码的人"的分界线。
