# 术语表

按"你什么时候会遇到它"排序。每条只讲大白话，不引入新术语。

## 第一层：现在就需要懂

**Repo / 仓库**
一个项目的文件夹，附带完整的修改历史。GitHub 上一个 repo 就是一个项目主页。

**Commit / 提交**
存一次档。每次 commit 会记录"谁、什么时候、改了哪些行、为什么改"。

**Branch / 分支**
从主线（通常叫 `main`）分出来的一条独立开发线。在分支上改坏了，主线不受影响，删掉分支重来即可。

**Fork**
把别人的仓库复制一份到你自己的账号下。原仓库不受影响。你想改别人的项目，第一步就是 fork。

**PR / Pull Request / 合并请求**
你在自己的分支上改好了，向原项目请求："收下我的改动吧。" 对方可以审查、讨论、要求你改，最后决定合不合。

**Issue / 问题单**
在项目里开一个帖子，报告 bug 或提需求。好的 issue 会写清楚：环境、复现步骤、预期结果、实际结果。

**Review / 审查**
项目维护者逐行看你的 PR，留下意见。你按意见改，改完再审，直到通过。

**Merge / 合并**
维护者点了合并按钮，你的改动正式进入项目。这时你的 PR 状态变成 "merged"，也是最值钱的结果。

**Maintainer / 维护者**
项目的负责人，有合并权限。多数是志愿者，无偿维护。

**Contributor / 贡献者**
给项目提过改动并被合并的人。项目主页通常有 Contributors 列表。

## 第二层：看项目时会遇到

**Star / 星标**
收藏按钮。数量代表关注度，但不等于质量，也不等于被使用。

**Fork 数**
有多少人复制了这个项目。比 star 更能说明"有人真的在改它"。

**README**
项目首页的说明书：这是什么、怎么装、怎么用。写不好会直接赶走用户。

**LICENSE / 许可证**
法律条款，规定别人能不能使用、修改、商用你的代码。常见的有 MIT（几乎随便用）、Apache-2.0（随便用，但要保留声明）、GPL（衍生作品也必须开源）。

**CI / 持续集成**
每次提交代码，服务器自动跑测试和检查。目的是"改动有没有把别的功能弄坏"。

**Release / 发布**
给用户一个可下载的正式版本，通常带版本号和更新说明。

**Semver / 语义化版本**
版本号 `1.2.3` 的含义：第一位是大改（不兼容），第二位是加功能，第三位是修 bug。

**CHANGELOG**
更新日志。用给人看的语言写"这一版改了什么"。

**CONTRIBUTING.md**
贡献指南。告诉想帮忙的人：怎么跑起来、代码风格、提交信息格式、PR 要求。

**good first issue**
维护者专门标给新手的简单任务，通常改动小、范围清晰。

**maintainer / owner**
看仓库的 `CODEOWNERS` 或 README，通常能知道谁说了算。

## 第三层：做 AI 相关项目会遇到

**MCP / Model Context Protocol**
一套标准接口，让 AI 能调用外部工具（读文件、查数据库、发消息）。可以理解成"AI 的插件规范"。

**MCP Server**
实现了这套接口的程序，提供一组"工具"给 AI 用。

**Skill / 技能**
一份 markdown 说明书，告诉 AI 遇到某类任务时该按什么步骤做。不写代码，写的是流程和判断标准。

**Agent / 智能体**
能自己规划步骤、调用工具、完成多步任务的 AI 程序（而不只是回答问题）。

**Prompt**
给 AI 的指令。写得好不好，直接决定输出质量。

**Token**
AI 处理文本的计量单位，一个汉字大约 1–2 个 token。上下文长度和费用都按它算。

**Context / 上下文**
AI 一次能"看到"的全部内容。太长会变慢变贵，还会遗忘中间部分。

**Hallucination / 幻觉**
AI 一本正经地编造不存在的东西。

**Eval / 评测**
用一批固定任务测试 AI 或工具的表现，用来比较改动前后是变好还是变坏。

## 第四层：项目运营会遇到

**Dogfooding / 吃自己的狗粮**
自己先用自己做的工具。好处是能第一时间发现难用之处。

**Launch / 发布推广**
项目第一次公开，通常配合一篇文章或视频。

**Roadmap / 路线图**
接下来打算做什么，按优先级列出。

**Backlog**
待办列表，通常就是一堆还没处理的 issue。

**Breaking change / 破坏性变更**
不兼容旧版本的改动，用户升级后原来的用法会坏。

**Deprecation / 弃用**
标记某个功能"以后会删"，给用户缓冲期。

**Regression / 回归**
以前好的功能，因为新改动又坏了。

**Flaky / 不稳定**
测试时好时坏，通常因为依赖了时间、网络或随机数。

## 一句话记忆法

- 想改别人的东西 → **Fork → Branch → Commit → PR → Review → Merge**
- 想让别人改你的东西 → 开 **Issue**，等人来
- 想证明自己靠谱 → 攒 **merged PR**
